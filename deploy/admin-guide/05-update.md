# 5. Обновление

Обновление — только подписанный офлайн-бандл, который администратор приносит на сервер сам
(`nmsctl update` ничего не скачивает). Для закрытых контуров это тот же файл.

## 5.1. Проверка релиза

Как при установке ([01-install.md](01-install.md), 1.2): проверьте подпись `SHA256SUMS`, контрольные
суммы и, если в релизе новый `nmsctl`, установите его до обновления — `nmsctl update` сам себя не
обновляет.

```sh
minisign -V -p minisign.pub -m SHA256SUMS
sha256sum -c SHA256SUMS
sudo install -m 0755 nmsctl /usr/local/bin/nmsctl
```

## 5.2. `nmsctl update`

```sh
sudo nmsctl update /srv/releases/nms-1.1.0.tar                 # подпись рядом: nms-1.1.0.tar.minisig
sudo nmsctl update --sig /srv/releases/nms-1.1.0.minisig /srv/releases/nms-1.1.0.tar
```

Шаги:

1. Бандл копируется в `/var/lib/nms/updates/<время>/` с проверкой подписи ключом релиза, вшитым в
   `nmsctl`. Неверная или отсутствующая подпись — отказ, **ничего не изменено**. Дальше читается
   только проверенная копия.
2. Сверка с манифестом (SHA-256 каждого образа), текущим тегом образов и диапазоном версий схемы БД.
3. Окно обслуживания: останавливаются все сервисы, которые пишут (executor, api, poller, eventd; gateway
   остаётся). Бэкап (БД и том состояния executor'а, как `nmsctl backup`) и копия `compose.yaml` — в тот же
   каталог. Сервисы не стартуют до успеха обновления или конца отката, поэтому откат ничего не теряет.
   Панель на это время недоступна.
4. `docker load`, новый тег в `compose.yaml`, миграции, `docker compose up --wait` (все health-check'и,
   до 10 минут).
5. Итог (успех или откат) записывается в аудит панели (`cli.update`).

Образ БД и сам `nmsctl` бандлом не обновляются.

## 5.3. Автоматический откат

Любой сбой начиная с перетегирования откатывает систему: прежний `compose.yaml`, пересозданные тома
БД и состояния executor'а, восстановление из бэкапа шага 3, старт стека. Команда завершается ошибкой
`update to X failed and was rolled back to Y`.

Если не удался и откат, `nmsctl` выводит путь к прежнему `compose.yaml` и к бэкапу в
`/var/lib/nms/updates/<время>/`. Этот бэкап зашифрован ключом установки; надёжный путь восстановления —
`nmsctl restore` из регулярного бэкапа на чистый сервер ([06-backup-restore.md](06-backup-restore.md)).
Поэтому перед обновлением сделайте `nmsctl backup`.

Каталоги `/var/lib/nms/updates/<время>/` с бэкапами остаются после обновления — удаляйте старые
вручную, чтобы не заполнить диск.

## 5.4. Ключ релиза (для мейнтейнера)

1. Создайте пару ключей офлайн (minisign 0.10+): `minisign -G -p minisign.pub -s minisign.key`.
   Секретный ключ никогда не попадает в CI или на сервер.
2. Публичный ключ (строка base64 из `minisign.pub`) — переменная репозитория `MINISIGN_PUBLIC_KEY`.
   CI вшивает его в `nmsctl` при сборке (`-ldflags "-X main.releaseKey=..."`). `nmsctl` без ключа
   отвергает любой бандл.
3. Тег `v*` запускает workflow `release`: неподписанный бандл `nms-<TAG>.tar`, `nmsctl` и
   `SHA256SUMS` (артефакт `release-unsigned`).
4. Офлайн, с файлами в одном каталоге:
   `scripts/sign-bundle.sh dist/nms-<TAG>.tar minisign.key minisign.pub` — подписывает бандл
   (`.minisig`, prehashed) и `SHA256SUMS` (`SHA256SUMS.minisig`) и сразу проверяет подписи.
5. Опубликуйте `nms-<TAG>.tar`, `nms-<TAG>.tar.minisig`, `nmsctl`, `SHA256SUMS`,
   `SHA256SUMS.minisig`; `minisign.pub` передайте заказчикам по отдельному доверенному каналу.

`nmsctl` подписан только через `SHA256SUMS`, поэтому операторы обязаны проверять его по шагу 5.1.
