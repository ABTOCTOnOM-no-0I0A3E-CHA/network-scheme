# 6. Бэкап и восстановление

Цель: RPO ≤ 24 ч (ежесуточный бэкап), RTO ≤ 2 ч по этой процедуре.

## 6.1. `nmsctl backup`

```sh
sudo nmsctl backup --out /srv/nms-backup
```

Создаёт два файла (`0600`):

| Файл | Содержимое | Чем защищён |
|---|---|---|
| `nms-backup-<время>.age` | Дамп БД, том состояния executor'а, якоря аудита, `keys.json` | age, ключ бэкапа установки `/etc/nms/secrets/backup_age.key` |
| `nms-keys-<время>.age` | Весь `/etc/nms`: конфиги, секреты, ключ бэкапа | age, парольная фраза (scrypt) |

- Парольная фраза — не короче 12 символов. Запрашивается дважды в терминале или берётся из
  `--passphrase-file F` (`-` — stdin). Храните её отдельно от архивов: архив ключей с фразой — это
  все секреты установки.
- Храните архивы вне сервера, архив ключей — отдельно от архива данных.
- На время снимка executor останавливается (изменения недоступны, панель работает). Если в момент
  бэкапа идёт изменение на устройстве, бэкап отказывает — повторите позже.
- Для ежесуточного запуска по расписанию нужен `--passphrase-file` (root, `0600`). Это ослабляет
  защиту архива ключей на самом сервере — учитывайте при выборе места хранения.

Проверяйте восстановление регулярно на отдельном сервере.

## 6.2. Восстановление на чистый сервер

Подготовка нового сервера — как для установки ([01-install.md](01-install.md), 1.1–1.3):

1. Требования к хосту: Docker 24+, `daemon.json`, свободные порты, NTP.
2. Проверенный `nmsctl` той же версии, что и бэкап, в `/usr/local/bin/nmsctl`.
3. **Образы уже загружены**: `nms/*` того же тега, что на исходном сервере, и тот же образ БД
   (версии PostgreSQL и TimescaleDB должны совпадать).
4. Сервер чистый: `/etc/nms` пуст или отсутствует, нет `/var/lib/nms/anchors` и
   `/var/lib/nms/gateway`, нет томов Docker проекта `nms`.

```sh
sudo nmsctl restore --data nms-backup-20261101T020000Z.age --keys nms-keys-20261101T020000Z.age
```

Что происходит: оба архива сначала расшифровываются и проверяются целиком; затем возвращаются
`/etc/nms` и файлы хоста, шаги хоста из установки (egress до старта контейнеров, drop-in Docker, таймер
якорей), БД, том состояния executor'а; стек стартует; в аудит пишется `cli.restore` и новый якорь;
последним выполняется `executor registry verify`.

Если восстановление прервалось: удалите `/etc/nms`, `/var/lib/nms` и тома
(`docker compose -f /etc/nms/compose.yaml down -v`), затем повторите.

## 6.3. Проверка после восстановления

После восстановления executor намеренно в freeze с причиной `host: restored from backup`: бэкап мог быть
старым (отозванные гранты, снятый freeze). Проверьте, затем снимите freeze осознанно.

```sh
sudo nmsctl executor registry verify     # реестр проходит
sudo nmsctl executor freeze off          # после проверки грантов и политики
sudo nmsctl audit verify                 # цепочка аудита панели и якоря
sudo nmsctl executor policy show
```

Затем войдите в панель и убедитесь, что опрос идёт.

- `--public-host` остаётся прежним: направьте DNS-имя на новый сервер.
- Если у нового сервера другой IP — обновите на устройствах ACL, адреса syslog и трапов
  ([03-devices-eltex.md](03-devices-eltex.md)).
- Если БД восстановлена без согласованного тома executor'а (не через `nmsctl restore`), executor
  уходит в freeze как при откате реестра — см. [08-incidents.md](08-incidents.md).
